# WP Easy Hub Connector

WordPress plugin, a separate repo from the Hub app (`../wpeasy-hub-app`, `app/Connector`, `ConnectorApiController`). Slug and folder `wpeasy-hub-connector`, namespace `WPEasy\HubConnector`, option `wpeasy_hub_connector` (never autoloaded), text domain `wpeasy-hub-connector`.

## Rules
- **Push by default, narrow signed calls where needed:** the plugin reports to the Hub; the Hub does not poll or pull from the site. The site has **no open API**: the only inbound requests are POSTs that must carry a valid signature, fresh timestamp and one-time nonce (or a login token), and only for a fixed list of actions (`Remote::ACTIONS`: `report`; plus the one-click login). Reason: every inbound door is attack surface, and a signed, single-action door is small and reviewable. A new Hub-to-site action needs: a signature check, a nonce claim (`Login::claim_nonce`), an entry in `Remote::ACTIONS`, a test, and a note here. Never add an unsigned or read-everything endpoint.
- **Never send more than the report** (versions, theme, plugin and theme names and versions, update versions, site URL). No users, content, settings or secrets.
- **Signatures:** `includes/Signature.php` must match the Hub's `app/Connector/Signature.php`; both assert the vector in `tests/signature-test.php` / `ConnectorTest`. Changing the format means a new version tag (`v2`) on both sides, never a silent change.
- Hub address: https only, except localhost, `.test` and `.localhost` for development. Requests never follow redirects.
- Admin actions are administrators only (`manage_options`) and nonce-checked. Escape all output.
- Plain, non-technical wording in everything a person sees. Brand: WP Easy.
- Version: edit the `Version:` header, the `VERSION` constant and `readme.txt` Stable tag together; `bin/build-zip.sh` builds the zip.

## One-click login
`includes/Login.php` + `includes/LoginToken.php`. Only a POST with a genuine, current, unused token signs anyone in; the user must still be an administrator; there is an off switch (`allow_login`, default on); failures are rate-limited by IP. "Works once" is an atomic `INSERT IGNORE` (`Login::claim_nonce`), never get-then-set (two simultaneous requests would both pass). Never accept the token in a GET address, never log it, never add another way to sign in. The report lists administrators by id, login and display name only (no emails).

## Updating things for the Hub
`Runner` (plugin, theme, core), `Backup`, `Health`. Rules learned by testing on a real site: **the answer must be JSON only**: WordPress's updater prints text, so `Remote` buffers all output (`ob_start`) and discards it; **`Automatic_Upgrader_Skin` has no `get_errors()`** (a call to it crashed the request right after the update: check the return value and `$skin->result` instead, `Runner::why_not`); anything unexpected mid-update must lead to the **put-back**, never a crash (try/catch Throwable around upgrade + check). **Never remove the backup-first step or the put-back**, and never update without a successful non-empty backup. Test every change to this on a throwaway site with a deliberate break (a mu-plugin that fatals once the new version is in place) and confirm the put-back.

## Updates
Through the Hub, never directly from GitHub: this repo is public and the plugin holds no secrets, and it only ever talks to its own Hub (`includes/Updater.php`, signed `GET`s). **Never put a token or any secret in this plugin or its zip** (the repo is public). Release with `bin/release.sh` (version header, `VERSION` constant and readme Stable tag must agree; the asset must be named `wpeasy-hub-connector-<version>.zip` with the plugin folder `wpeasy-hub-connector/` inside, which `bin/build-zip.sh` does).

## WP-CLI
`includes/Cli.php`: `wp wpeasy-hub connect --code=<code> [--hub=<url>]` and `wp wpeasy-hub status`, loaded only when `WP_CLI` is defined. It uses the same `Client::pair` as the settings page. Command line only: whoever can run it already controls the website, and it adds no way in from the web.

## Backups (0.5.0)
`includes/Backup.php`: every backup is ONE ZIP FILE (never loose copies: a zip is not run as code, so an old vulnerable copy cannot be called through the web even if the folder is open). Kept OUTSIDE the document root when the host allows it (the folder above WordPress, only decided during a real web request, remembered in the option as `backup_dir`), else in `uploads/wpeasy-hub-backups-<random token>` with `.htaccess`, `web.config` and `index.php` deny files (nginx ignores `.htaccess`, so the unguessable name and the zip form are the real protection there). Newest 2 per item, nothing older than 14 days (`KEEP`, `KEEP_DAYS`), cleared by a daily WP-Cron job (`BACKUPS`) and once after each new version arrives (`backups_version`): `Backup::maintain()` = convert the loose folders versions before 0.5.0 left in `uploads/wpeasy-hub-backups` (recent ones become zips, the rest are deleted, the old folder goes), keep the newest two per item, delete anything past 14 days. `sanitize_file_name` trims a trailing dash, so file-name prefixes are built as `sanitize_file_name( kind-slug ) . '-'`. The report carries `backups` {count, bytes, outside, loose}; uninstall deletes the backups. Never write loose plugin files into the web-visible tree.

## Removing things for the Hub
`includes/Remover.php`, Remote action `remove` (kind plugin|theme, id): only something NOT in use, never the connector or the parent of the active theme, backup first (an empty backup stops it), WordPress's own `delete_plugins` / `delete_theme`. The answer is JSON only (`ob_start`); the report is sent afterwards. Deleting runs the plugin's own uninstall routine, which may delete its data: the backup is of files only.

## Not built yet
One-time login from the Hub, running updates from the Hub, a report on demand from the Hub (needs an endpoint on the site), per-plugin details beyond name and version, translations (strings are already wrapped).

## Website backups (0.7.0, 2026-11-19)
The Hub backs a website up through five more signed actions (`SiteBackup::ACTIONS`, same signature and nonce rules as `report`): `backup_info`, `backup_dirs {paths[]}` (lists folders, the Hub walks the tree), `backup_files {items:[{p,o,l}], max}` (binary frames: `WPEHB1\n`, then per file a JSON header line, the bytes, a newline, and a final `{"end":true}`), `backup_tables`, `backup_rows {table,cursor,rows,max}` (SQL for one page of a table; keyset cursor on a single-column primary key, else offset; binary and non-UTF-8 values as hex). **Everything is stateless and read-only**: only paths `BackupPaths` allows (wp-content plus wp-config.php, .htaccess, robots.txt; never symlinks, caches, other backup tools, logs, .git, node_modules; WordPress core is not backed up), only SELECT/SHOW queries, only tables with this site's prefix. The setting "Let the Hub back up this website" (`allow_backup`, default on) switches it off; the report carries `backup_allowed`. This is the one exception to "send nothing but the report": the Hub may READ files and rows, only when it asks and the website allows it. Request bodies may be 64 KB (the signature is checked first). `tests/backup-test.php` covers paths, symlink escapes, frames and a dump that restores exactly (needs the Hub's MariaDB `testing` database, skipped without it). Keep this code PHP 7.4 compatible. Not built: restore.

- **0.7.2 (2026-11-19): backups cover the whole site folder.** `BackupPaths::roots($core)` lists every entry in the WordPress folder, hidden files included (.htaccess, .user.ini, .well-known), except WordPress core (`wp-admin`, `wp-includes`, the loose core PHP files) unless the Hub's request carries `core: true` (a per-site Hub switch), plus `.git`, `.svn`, `node_modules`, logs, symlinks and a few host folders (`backups`, `cgi-bin`); wp-content is taken from `WP_CONTENT_DIR`. `backup_dirs`, `backup_files` and `backup_info` all accept `core`.

## Restore (0.8.0, 2026-11-19)
Signed actions `restore_begin`, `restore_dirs`, `restore_files`, `restore_sql`, `restore_core`, `restore_finish` (`SiteRestore::ACTIONS`; switch "Let the Hub restore a backup onto this website", `allow_restore`, default on, report `restore_allowed`; request bodies may be 2 MB). **Rules:** writes only inside the site's own folders (`RestoreGuard`: no `..`, no symlinks, no folders, not core unless `core` is sent, never `wp-content/plugins/wpeasy-hub-connector`, never `.maintenance` or `*.hubtmp`, never the places a backup excludes); files arrive in pieces into `<name>.hubtmp` and replace the real file only when size and sha256 match (`RestoreFiles`), with permissions and modified time put back; **nothing is ever deleted**; tables are restored only by running the statements a table backup contains (SET lines, DROP TABLE IF EXISTS, CREATE TABLE, INSERT INTO for exactly that table, found with the quote-aware `SqlSplitter`, all checked before any runs, `RestoreDb`); core is reinstalled with WordPress's own `Core_Upgrader` (`RestoreCore`). `restore_begin` puts the site in WordPress maintenance mode (renewed by every restore request; WordPress drops it after 10 minutes without one) and keeps this plugin's own settings aside, `restore_finish` puts the pairing back (a restored options table holds the old one), flushes caches and ends maintenance. `restore_begin` also returns `free_bytes`. Tests: `tests/restore-test.php`.
